### S5-20261124-10 — Medium (maps to Major) — The dispatch stand-in keeps buyer PII past the limit (= F-M10-end-06)
IDs: DEL-1, ORD-4, TEN-6, PRD 7.3 (FA-16)  CWE-212

I had this as needs-validation 2. That was too low: the code breaks PRD 7.3 whatever eBay's spec says. S4 is right that it is a Major.

Evidence (probed); the last two cases go beyond F-06's text:
- F06a: eBay, placed 89 days ago, first seen FULFILLED, edited yesterday: placement + **113** days.
- F06b: website, the same, `shipped` with no `shipped_at`: placement + **113** days.
- F06c: an eBay order **already stored** with the 90-day backstop, first seen FULFILLED at day 80 (a polling gap): `orders.pii_expiry` moves it **later**, from placement + 90 to placement + **105**.

Required fix:
1. Placement + 90 days is a hard cap on every date, at ingest and in `orders.pii_expiry`. One helper, used by both. This is S4's bound; I agree with it and it is the simplest rule. (Strictly, PRD 7.3 puts the 90 days on undispatched orders only. The cap deletes earlier than that for an order shipped after day 65, which is the safe side. S1 notes it.)
2. A first-seen shipped order with no real dispatch time: use ship-by, else placement, never the last edit. Past the window, no vault record. The eBay adapter returns `dispatchedAt: null` for FULFILLED, so that `effectiveDispatch` can tell a real date from a stand-in.
3. For an order already stored as unshipped, the first update that shows it shipped is an acceptable stand-in, under the cap in 1. It may shorten the date and must not lengthen it past the cap.

Tests: F06a, F06b and F06c, through the parsers, seen red first.
Resolution: fixed in T-1003. `piiExpiryDate()` (`apps/worker/src/orders.ts`) is the one sum, used at ingest and by `orders.pii_expiry`, and never passes placement + 90 days. `effectiveDispatch()` is told whether the order was already stored unshipped; first seen shipped it uses the earlier of ship-by and the update, or placement. The eBay adapter gives no dispatch time for FULFILLED. F06a, F06b and F06c are red-first tests through the parsers, with a real but late date as well.

### Ruling on F-M10-end-18 (deleted_buyers not journalled)

**Confirmed by running it. Minor, part of -08.** F18: a notice, then the buyer refused; then the table emptied (as after restoring an older backup) and the real `apply-tombstones.sql` run with the real journal. Result: 0 lines for it, 0 rows rebuilt, and the same buyer is **stored**. F18b shows the limit: an order db-main already knows is not fetched again and stays deleted (0 records), so only buyers of orders unknown to db-main come back. That means both databases restored, or the 90-day backfill of an account connected later.

It is not a Major now, as no real data exists. It is a condition of T-1501 going live, because eBay does not send a notice again once it was answered 200. **Correction:** the option in -08 to have notices "asked for again" does not exist; journalling is the only fix.

Required fix, with PS-035 and not before it (the table is being redesigned):
1. Before the commit, journal one line per entry: `{type: 'ebay_deleted', field, mac, key_version, at}`. No user ID or username. Replay inserts it, keeping the newest date.
2. A key made after the backup is lost by the restore, and then the MACs match nothing. The vault-wide key of PS-035 is made before any real data, so it is in every backup. With today's per-workspace keys a replay would not work for a newer workspace. This is one more reason for PS-035.
3. S1 widens invariant 10 from "IDs only" to "IDs and these MACs". Without the index key, which is never in the journal, a MAC says nothing.
4. Replay deletes the rows of a closed workspace, if the table stays per workspace.

Test: the F18 probe, and V12 (the newest journal line wins).

## S5-20261124-01 — Medium (maps to Major) — A website order first seen as shipped, with no ship date, keeps buyer PII for up to 90 days instead of 25
IDs: DEL-1, TEN-6, AT-8, PRD 7.3 (FA-16)  CWE-212, OWASP A04
Evidence:
- `piiDeleteAfter` (`apps/worker/src/orders.ts:47-56`) uses `deliveredAt ?? dispatchedAt`. The website parser gives state `dispatched` with `dispatchedAt: null` for `status: 'shipped'` or `'completed'` without `shipped_at`. The vault then gets placement + 90 days.
- `OrderIngest.#create` (`packages/db/src/orders.ts:343`) fills `dispatched_at` from `updated_at`, but only `#update` calls `shortenPii`. The stand-in date never reaches the vault.
- P1: placed 40 days ago, shipped 38 days ago, no `shipped_at`. Result: `status = dispatched`, the record is kept for **88 days after dispatch** (50 days from now), and no `orders.pii_expiry` job is queued. With `shipped_at` present (P1b) the same order correctly gets no record.
Impact: a shipped buyer's name, address, phone and email live past the "every copy gone by day 30" promise, with no job that corrects it. FA-16 (no record for orders past the window) is missed in the same way.
Required fix: work out the effective dispatch date once, before the vault call, and use it in both places: `dispatchedAt ?? (state is dispatched or delivered ? deliveredAt ?? updatedAt : null)`. `#create` must also call `shortenPii` whenever it stores an order that is already shipped and has a `pii_ref`, so one path cannot drift from the other.
Tests: a website order first seen shipped with no `shipped_at` gets `updated_at` + 25 days; one past that date gets no record.
Resolution: Fixed in #160. `effectiveDispatch()` (`packages/db/src/orders.ts`) is the one dispatch date, used by the vault-first step and by db-main. `#create` calls `shortenPii` for an order first stored shipped, and `#update` does when a record joins an order that already shipped. Tests: "a website order first seen shipped with no ship date…", "a record written before the order shipped is corrected…" (worker, through the parser), "an order first stored already shipped…", "a record that arrives after the order shipped…" (db). Closed for good by -10 in T-1003; the test that expected `updated_at` + 25 days now expects placement + 25 days (S1, 25 Nov).

## S5-20261124-02 — Medium (maps to Major) — An order's buyer record is frozen at first sight, even when it holds only a username
IDs: ORD-4, DP-5 (supports SHP), UK GDPR Art. 5(1)(c) and (d)
Evidence:
- `ebayBuyer` is never null, because `buyer.username` is always sent. A `PENDING` order with no ship-to block is therefore ingested with `channel_username` alone. `piiState` then calls it settled (`orders.ts:223`, `pii_ref IS NOT NULL`), and the vault keeps the first record (`vault.ts:204`).
- P2: eBay order PENDING with no address, then PAID with the full address. The vault record still holds only `["channel_username"]`. S3's review fix 1 is tested with `buyer: null`, which the eBay parser does not produce when a username is sent.
- P2b: an address corrected by the channel after first sight never reaches the vault; `readFull` for a label returns the old one.
Impact: a paid order with no address cannot be shipped, and nothing repairs it. A corrected address is ignored, so a label sends one person's details and parcel to another address. PII of buyers who never pay is also stored for nothing.
Required fix:
1. Do not send `pending_payment` orders to the vault, and do not settle an order until its buyer block has a delivery address (`address_line1` and `postcode`). Until then the answer is `none`.
2. Corrections before dispatch: S1 rules whether the one record is updated in place (fields and blind indexes replaced under the same `pii_ref`, never after a deletion) or the limit is documented. Suggested: update in place. No change is needed after dispatch.
Tests: the two P2 cases, through `parseEbayOrders`.
Resolution: (1) fixed in #160: nothing is sent for `pending_payment`, and nothing is settled without a delivery address. The address is the first line plus the postcode; outside the UK the town also counts, because some countries have no postcodes. Tests: "an unpaid order sends nothing…", "a paid order with no delivery address yet…", "a delivery address abroad…", all through `parseEbayOrders`/`parseWebsiteOrders`. (2) OPEN: waits for S1's ruling on corrections before dispatch. (2) fixed in T-1003: `POST /v1/replace` (worker token) updates the one record in place, same ref and `delete_after`, with its blind indexes and match key, for an order that is paid and waiting on both sides. It never makes a record; an older update, a masked or partial block, an expired or deleted record, a closed workspace and a deleted buyer change nothing. The delivery block is replaced whole; an email, phone or channel ID not sent again is kept.

## S5-20261124-03 — Medium (maps to Major) — The deleted-buyer check misses four cases, so a buyer removed by an eBay notice can be stored again
IDs: DEL-1, AT-10, EBAY-2 (ADR-068, ADR-079 3)  CWE-362, CWE-459
Evidence (each one probed):
- **(a) No keys yet (S3's b).** `workspace_directory` gets a row only when a workspace makes keys, so a notice never visits a workspace that has not ingested. P3: notice first, then the first ingest by user ID and by username: **both stored**. This is the normal case for a newly connected account with a 90-day backfill.
- **(b) Race.** Ingest checks the tombstone under the shared workspace lock, but `ebayUserMatch` takes no lock. P8: with an ingest held between its check and its commit, the notice matched **0** records, and **1 record stayed** afterwards. Nothing looks for it again until its normal expiry.
- **(c) User ID in the username slot.** Matching for deletion compares both the ID and the username with `buyer_exact`, but the refusal compares `channel_username` only with the username tombstone. P4: a username field holding the deleted user's ID is **stored**; the same value in `channel_buyer_id` is refused. eBay orders carry only `channel_username`, so the stronger ID tombstone never applies to them today.
- **(d) Second notice for a username.** `ON CONFLICT DO NOTHING` keeps the first date. P5: the second owner of a reused username is deleted too, and that owner's order placed between the two notices is **stored**.
Impact: eBay account-deletion data reappears after the notice was answered 200. It is bounded by the normal expiry (up to 90 days for an undispatched order), but eBay allows 30 days.
Required fix (a design choice for S1; S3 writes the Proposed row):
1. Suggested and simpler: one vault-wide tombstone table with its own index key, wrapped under the PII master key and separate from workspace keys. Each notice writes its row once, before the first workspace is visited, and ingest checks it in every workspace. This closes (a) and gives (c)/rotation and -08 one place. It is kept when a workspace closes. Alternative: keep the per-workspace table, and also make keys and a directory row for every workspace with an eBay account.
2. `ebayUserMatch` takes `pg_advisory_xact_lock(workspaceLock)` exclusively, per workspace, after the tombstone commits and before it reads the index. In-flight ingests then finish first and are matched, and later ones see the tombstone.
3. An ID tombstone refuses a match in `channel_buyer_id` **or** `channel_username`. A username tombstone keeps the placed-before rule.
4. A repeat notice moves the username's date forward (`GREATEST`), with UPDATE granted on that column only.
Tests: P3, P4, P5 and P8 as tests; P8's gate is a pool wrapper that pauses before `INSERT INTO vault.records`.
Resolution: (b), (c), (d) fixed in #160 (db-pii 0010): `ebayUserMatch` takes the workspace lock alone before it writes the tombstone and reads the index, in one transaction; an ID tombstone refuses either field; a repeat notice moves the date forward (UPDATE granted on that column only). Tests: the three "[DEL-1][AT-10]" tests in `vault.int.test.ts`, the race with a paused ingest. (a) OPEN: PS-035 waits for S1. (a) fixed in T-1003 (PS-035): one vault-wide table (db-pii 0011) under a key of its own, made before the vault serves; every buyer write holds a vault-wide lock shared from before its check to its commit, and the notice takes it alone, commits its entries and only then reads the directory. Tests: a notice before any workspace holds anything, and the first ingest of a new workspace paused after its check.

## S5-20261124-04 — Medium (maps to Minor, fix now) — Late mapping of 7 or more lines loses a VAT ledger row
IDs: VAT-2, VAT-3, FIN-1 (FA-11)  CWE-222
Evidence: the adjustment key is `adjust:<order>:<line ids, comma-joined>:<group>` cut to 300 characters (`packages/db/src/orders.ts:790`; same in `#rebaseRefunds`, `:871`). With 7 lines of one listing the group is cut off, both groups get the same key, and the second insert hits `ON CONFLICT DO NOTHING`. P11, mapped to zero-rated: 6 lines write `-7200/-1200` and `+7200/0` (ledger gross 7200, correct); 7 and 8 lines write **only the negative row**, so the ledger gross is **0** against an order gross of 8400 and 9600.
Impact: sales, and for a reduced-rate SKU output VAT, silently vanish from an append-only ledger the app cannot correct. No error is raised.
Required fix: no truncation. Use a fixed-length key: the SHA-256 of the line IDs, with the group key kept in full. Also make the conflict clause unable to hide a difference: after the insert, zero affected rows with different amounts is an error.
Tests: 8 lines of one listing mapped to zero and to reduced; the ledger equals the order's gross and VAT.
Resolution: Fixed in #160: the key holds a SHA-256 of the lines filled, with the group in full, and a conflict with a different entry is an error. Tests: "mapping many lines of one listing at once…" (8 lines, zero and reduced, with a refund re-based), "a ledger key taken by a different amount…".

## S5-20261124-05 — Medium (maps to Minor, fix now) — Channel amounts lose their sign or part of a refund, and the channel total is never checked
IDs: FIN-1, VAT-3, VAT-5 (invariant 12)
Evidence:
- `penceFromAmount` drops a minus sign everywhere, not only on discounts (`money.ts:9`). P12b: a website line of `-5.00` becomes **+500**, and a refund of `-4.00` becomes **+400**.
- P12: refund of £15.00 whose lines hold £12.00 (the rest is shipping): the ledger takes **-1200/-200**, while £3.00 (50p VAT) is left out. `computeRefundVat` ignores `amount - sum(lines)`.
- P12c: eBay `deliveryDiscount` and `adjustment` are not read. Buyer paid 1200; stored gross is **1500**. `pricingSummary.total` is parsed and never used.
Impact: VAT overstated or understated with no signal.
Required fix: `PenceAmount` and `GbpAmount` refuse a minus; only the discount fields use a signed variant. The part of a refund not covered by its lines is split across the order's rate groups like a refund without line detail (S1 confirms against VAT-5). Read `deliveryDiscount` and `adjustment`. When the computed gross differs from the channel's total, flag the order or raise a notice, and do not accept it silently. T-1501 fixes the exact eBay rule.
Resolution: Fixed in #160: `PenceAmount` and `GbpAmount` refuse a minus; discounts and adjustments have their own types. The part of a refund its lines do not cover splits pro-rata; lines never give back more than the refund; what a group cannot take spills to the others. `deliveryDiscount` and `adjustment` are read. A stored gross that differs from eBay's total is logged and raises one platform notice per account (the website protocol states no total until M11). Tests: `vat.test.ts`, `money.test.ts`, both parser tests, "an order whose pence differ…" (db) and "…raises one platform notice" (worker). S1 to confirm VAT-5. Follow-up: a flag users see on the order.

## S5-20261124-06 — Low (maps to Minor) — A record the orphan sweep has expired is handed back to a live order
IDs: ORD-4, DEL-1 (FA-10)

## S5-20261124-07 — Low (maps to Minor) — One order that cannot be stored stops all order sync of its account
IDs: INT-5, CAP-6  CWE-754
Evidence (P7), each failing the whole run: an external ID of 170 characters (parser allows 200, but the vault `subject_id` and `orders.pii_subject` hold 200 **including** the 37-character account prefix) → 422; an order with no lines and a shipping charge → RangeError; a NUL in a title → PostgreSQL error; delivery instructions over 4,000 characters → parser failure. ## S5-20261124-08 — Low (maps to Minor) — `vault.deleted_buyers` grows without limit and has no restore path
IDs: DP-5, DEL-2, EBAY-2  CWE-459
Evidence: eBay sends a notice for every closed eBay account, held or not. P9: 10 notices for users never seen wrote **40 rows** in 2 workspaces. Nothing ever purges them. The MACs are pseudonymous personal data. A restored db-pii loses the tombstones made since its backup (they are in no journal), and `apply-tombstones.sql:76` re-closes a workspace without deleting its rows.
Impact: pseudonyms of people who were never customers are kept for ever; write load on a 3-second webhook; a small re-ingest gap after a restore.
Required fix: purge tombstones after 180 days (no order placed before the notice can enter the vault after that; pick the figure with S1), in the daily ops purge. With the vault-wide table of -03 this is one row or two per notice. Journal the MAC, field and date (no value) like the expiry lines and replay them (the alternative I first gave here was wrong; see the Update). Add the missing DELETE on closure replay.
Resolution: fixed in T-1003: entries go 180 days after the last notice in the daily purge (a definer function, no DELETE for the vault); each entry is journalled before its commit (MAC, field, dates, key version) and replayed by `apply-tombstones.sql`. A restore from a backup older than the entry refuses the buyer (`restore.int.test.ts`). The table is vault-wide and kept on closure, so closure has no rows to delete in it.

## S5-20261124-09 — Low (maps to Minor) — The index-key rotation gap in the tombstone check (S3's c)
IDs: DP-6 (M22)
Evidence: `#refuseDeletedBuyer` computes MACs with `keys.index`, and `#loadKeys` reads only `KEY_VERSION = 1`. There is no rotation today, so this is not reachable. After a rotation every older tombstone would stop matching, silently. A tombstone's value is not kept, so its MAC cannot be recomputed under a new key.
Required fix (with -03, or in the M22 rotation task): look tombstones up under every index-key version that has tombstones, and keep an old index key until its last tombstone is purged (-08). A rotation test that a pre-rotation tombstone still refuses.
Resolution: lookups go through every stored key version (T-1003, tested with two). Rotation itself stays in M22.

## Checked and sound

1. **PII only to the vault.** P13 marked the buyer fields of eBay and website orders, plus unknown ones (notes, billing address, tax address). Markers found in db-main (app and pgboss schemas), logs, captured payloads and the journal: 0; in plain text in db-pii: 0. `prepare` nulls `buyer`, `toIncoming` has no buyer field, and parser errors hold a path only. `orders.pii_expiry` and `pii.delete` payloads are strict and hold IDs. Weakness in S3's scan: its queue is a stub, so the pgboss part scans an empty table. Use a real queue in one test.
2. **Vault.** One record per order (unique index), idempotent. `/v1/subjects`: worker 200, web and deletion 403, another workspace gets an empty list (P14). Expiry journal lines hold IDs and dates, fsynced before commit; the newest wins on replay, tombstones first, and it is safe to run twice. Closure deletes `deleted_buyers` with the keys. RLS is forced; vault_app has no UPDATE on it.
3. **Retention.** Placement + 90, dispatch or delivery + 25, no record for cancelled or past-window orders, cancellation deletion by subject: correct except -01 and -06. The orphan sweep reads all companies (`workspace_company_ids`), so company RLS cannot make a live order look lost. An order cancelled while its record is an orphan waits for the sweep, about 2 days, inside the 30-day limit.
4. **Money.** All 'pence' columns in `app` are bigint (P10c). GBP only, by text. No role of the app (ob_app, ob_worker, ob_tenant_rw, ob_ops, ob_auth, ob_platform) has UPDATE, DELETE or TRUNCATE on `vat_ledger`, `refunds`, `refund_lines` or `order_status_events` (P10). Snapshots are write-once by trigger.

## Hardening notes

1. `/v1/expiry` answers 200 to web's token (P14), though only the worker uses it, and the vault does not limit the date against the record's creation, so a repeated call can keep a record alive. Limit it to the worker.
2. A delivery or dispatch time in the future from a channel is only capped at now + 90 days. Cap it at now.
