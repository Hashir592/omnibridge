## Confirmed findings

## S5-20261118-01 — Medium (maps to Major) — Deletions made since the last nightly backup come back after a full-host restore
IDs: DEL-2, AT-8 (supports DEL-4, AT-10)  CWE/OWASP: CWE-212, OWASP A04 Insecure Design
Evidence:
- Invariant 10 asks for tombstones in three places, one of them an **off-site** journal, so a
  restore can re-apply every deletion. The journal is written on the host
  (`apps/pii-vault/src/deletion.ts:41`, volume `pii_journal`) and leaves the host only inside the
  nightly `backup.sh` run (`infra/backup/backup.sh:28`), the same run that dumps db-main and db-pii.
  `infra/backup/b2.md` and STATE's M22 note schedule only that nightly run.
- So all three tombstone copies of a deletion made at 14:00 sit on the same host until the next
  night: db-pii's `vault.tombstones`, db-main's `app.pii_tombstones`, and the journal file.
- Lineage after a full-host loss at 18:00: restore runs from last night's dumps
  (`docs/ops/runbooks/restore.md`); the restored db-pii still holds the record; neither restored
  database nor the restored journal (`restic restore --tag journal latest`) holds its tombstone;
  `apply-tombstones.sql` therefore keeps it. The record is live again.
Impact: an erasure the admin confirmed (DEL-4), an eBay account deletion (AT-10, which eBay never
re-sends after our 200) or a cancellation deletion made on the day of a disaster is undone by the
restore. DEL-2 says "deleted data never comes back". No attacker needed; the trigger is a
host loss, so likelihood is low, but the result is a compliance breach that cannot be detected
afterwards (nothing records that the deletion happened).
Required fix: ship the journal off-site soon after each write, not nightly. Simplest: a
journal-only command (`infra/backup/journal.sh`, the existing `restic_run main … backup --tag
journal /journal` step on its own) scheduled every 15 minutes in M22, with the restore runbook
stating the window ("deletions in the last 15 minutes before a host loss must be re-run from the
deletion runs list"). Add the 15-minute schedule to the M22 backup task and to `b2.md`. Test (drill):
a deletion made after the last full backup but before the last journal run is re-applied by
`restore-drill.sh`.

## S5-20261118-02 — Low (maps to Minor) — Confirm and withdraw can race: records are deleted while the request says "withdrawn"
IDs: DEL-4, DEL-3 (supports ADR-067)  CWE/OWASP: CWE-367
Evidence:
- `apps/web/src/privacy.ts:119-146` (confirm): reads the request (`erasures.get`, its own
  transaction), then `requestDeletion` commits the `pii.delete` job (its own transaction,
  `packages/queue/src/runtime.ts:198`), and only then runs the conditional
  `UPDATE … WHERE state = 'open'` (`packages/db/src/erasure.ts:141-156`).
- A withdraw (`privacy.ts:158-169`, `erasure.ts:112-133`) that commits between the job insert and
  that update wins: confirm gets `undefined` and answers 409, but the job is already queued and the
  worker deletes the refs (`apps/worker/src/deletion.ts` does not look at the request's state).
- Reproduce (local, two admins of one workspace, or one admin in two tabs): start a request; send
  `POST /erasure-requests/:id/confirm` and `POST /erasure-requests/:id/withdraw` at the same time
  (repeat a few times). Some runs end with the request `withdrawn` (reason e.g.
  `wrong_identifiers`) and its `pii.delete` job `completed`. Not run live in this audit; the
  ordering is clear from the code.
- The same end state follows from a db-main error on the confirm `UPDATE` after the job commits:
  the request stays `open`, and a later withdraw marks it withdrawn although its records are gone.
Impact: the case where withdraw matters most ("wrong identifiers": the matches are other buyers)
is the one where the race deletes other buyers' records, irreversibly, while the DEL-3 record says
nothing was deleted. Needs two near-simultaneous admin actions, so Low.
Required fix: claim the request first, then queue. Confirm runs the conditional update to
`confirmed` (with `job_id` null) first; 409 if it is not open; then `requestDeletion` (idempotent
on the request id); then sets `job_id`. A confirm of a `confirmed` request whose `job_id` is null
re-queues (same key) instead of 409, so a failed queue call can be retried. Test: `[DEL-4] a
withdraw that races a confirm never leaves a withdrawn request with a deletion job`.
Resolution:

## S5-20261118-03 — Low (maps to Minor) — The AT-9 marker scan cannot see app logs, and the drill scans only mail summaries
IDs: AT-9, DP-8  CWE/OWASP: CWE-532 (detection gap)
Evidence:
- The logger replaces every `PIIMARK-…` token with `[REDACTED]` before writing
  (`packages/logger/src/logger.ts:62,75-81`), and its own test asserts the marker never appears in
  output (`packages/logger/src/logger.test.ts:19-31`).
- The boundary tests capture that same logger's output and assert no marker in it
  (`apps/worker/src/pii-boundary.int.test.ts:131`, `apps/web/src/privacy.int.test.ts:523`), and the
  drill scans `docker compose logs` (`infra/backup/restore-drill.sh:66`). These checks pass by
  construction for anything that goes through the logger.
- The scrub removes only the token up to the first space: `PIIMARK-Jane Doe` logs as
  `[REDACTED] Doe`. In production a real name has no marker, so the same path logs `Jane Doe` in
  full. The test that should catch that path is the one that is blinded.
- The drill reads mail from `GET /api/v1/messages?limit=500` (`restore-drill.sh:69`), Mailpit's
  list endpoint, which returns headers and a short snippet, not the body. A marker past the
  snippet is not scanned. (`packages/mail/src/mailpit.int.test.ts:56` reads the raw message and is
  fine.)
Impact: a future change that logs a buyer value through an allowed field (`err`, `status`,
`route`) or mails one in a body passes CI and the drill, then logs or mails real PII in
production (invariant 7). No leak found today; the detector for it is off.
Required fix: keep the scrub, make it visible. Replace the marker with a fixed token the scans also
look for, for example `[PIIMARK-REDACTED]` → the scan flags `PIIMARK` (drop the trailing `-` from
`MARKER` / `PII_MARKER`); update `logger.test.ts` to expect the token. In the drill, fetch each
message's raw source (`/api/v1/message/{ID}/raw`) for the scan. Test: `[AT-9] a marker logged
through an allowed field is found by the scan`.
Resolution:

## S5-20261118-04 — Low (maps to Minor) — One weak identifier exports up to 500 buyers' full details, or queues them for erasure
IDs: DEL-5, DEL-4 (supports DP-7, DP-8)  CWE/OWASP: CWE-359
Evidence:
- `BuyerIdentifiersSchema` needs any one field (`packages/contract/src/routes/privacy.ts:21-32`).
  Postcode alone or name alone is accepted.
- `exportSubjectAccess` (`apps/web/src/privacy.ts:188-247`) searches by it and reads every match in
  full (`purpose: subject_access`), up to `MAX_EXPORT_RECORDS = 500`, into one JSON file. A
  postcode matches every buyer at that postcode on every channel.
- `createErasureRequest` does the same search; confirming deletes every match (up to 5000).
Impact: the one bulk export of full PII that DP-8 allows (for one buyer who asked) can be pointed
at a whole postcode: an admin's session (or a stolen one) leaves with up to 500 buyers' full
details per request, each read logged but nothing refused. On the erasure side the same weak query
puts unrelated buyers one click from deletion (the masked list helps, but one postcode can match
hundreds). Admin-only, so Low.
Required fix: require identifiers that pin one person: at least one of `email`, `phone`, `buyer`,
or both `name` and `postcode`; else 422 with "Add the buyer's email, phone or marketplace ID, or
their name and postcode". Same rule for both routes (one refine on the schema). Lower
`MAX_EXPORT_RECORDS` to 100. Test: `[DEL-5] a postcode alone is refused for an access export and
an erasure`.
Resolution:

## Needs validation

1. **Expiry changes are not journalled (restore).** `setExpiry` (`vault.ts:195-204`) shortens
   `delete_after` in db-pii only. After a restore, a record whose expiry was shortened since the
   backup gets its older, later expiry back (up to the 90-day backstop), past the day-25 promise
   (P-010). No caller exists yet. **To check (M10):** after a restore, M10 re-derives
   `delete_after` from db-main's dispatch and delivery dates and calls `setExpiry` again (one line
   in the restore runbook), or the journal records expiry changes.
2. **Re-ingest after deletion.** After an eBay account-deletion notice, a later order sync or
   message sync of that user's past orders would ingest the PII again (ingest does not look at
   tombstones). **To check (M07, M08, M10):** ingest skips a subject whose records were deleted by
   `ebay_account_deletion` (eBay keeps sending the old orders), and the M10 test covers it.
3. **eBay username reuse.** Orders carry the buyer's username, so most records' `buyer_exact` is a
   username, and the notice is matched on it. **To check (M08):** whether eBay can ever give a
   username to a different user, and whether the order APIs expose the immutable user ID to store
   as `channel_buyer_id` instead.

Rejected after reading the code and its tests (for the record): a `pii_ref` of workspace B read
with workspace A's id (RLS plus the `workspace_id` predicate: 404); worker token on `/v1/search`,
`/v1/delete` or `/v1/ebay-user-match`, deletion token on any read, web token on `/v1/delete`
(403, `auth.ts:10-25`, `app.ts:217-227`); a token compare oracle (SHA-256 digests,
`timingSafeEqual` over every caller); the canary in search or the eBay match (no blind index;
`NOT r.canary`); swapping an erasure request's refs (no UPDATE grant on `pii_refs`; vault deletes
only refs in the request's workspace); identifiers in URLs or stored in db-main (bodies only; refs
stored); the access export cached or sniffed (`private, no-store`, `attachment`, `nosniff`); ingest
racing closure (shared/exclusive advisory lock, closed marker, 409); keys left after closure
(deleted last, cache dropped, re-deleted by the restore SQL); nonce reuse or ciphertext moved
between rows or workspaces (random 96-bit nonce per field; AAD binds workspace, table, column, row);
the PII master key in a backup (Docker secret only, not in the dump); an eBay notice deleting a
same-named Amazon or website buyer (exact index, filtered to the workspace's eBay accounts);
withdraw or confirm by a non-admin (`adminOnly` plus RESTRICTIVE RLS in 0025).

## Hardening notes

1. **The vault can reach the internet.** pii-vault joins `ob_app`, which is not `internal`
   (`infra/compose/compose.yaml:349,385`). The vault needs no egress. Put web, worker and the vault
   on an internal `ob_vault` network for vault calls, and drop the vault from `ob_app`.
2. **JSON API responses carry no `Cache-Control`.** Only file downloads send `no-store`
   (`apps/web/src/contract.ts:488`). Set `Cache-Control: no-store` on every `/api` response in one
   hook before M10's order detail returns full PII.
3. **`setExpiry` can move the canary.** The `UPDATE` has no `AND NOT canary`
   (`vault.ts:199`); a caller holding the canary's ref could make the expiry job delete it. One
   predicate.
4. **Access log retention.** `vault.access_log` and `vault.canary_events` keep `actor_user_id`
   forever, also after workspace closure (no DELETE grant). Staff user IDs are personal data in a
   small way; S1 to set a retention (for example 2 years, purged by the ops role).
5. **VACUUM does not wipe bytes.** VACUUM frees dead tuples but does not zero page free space or
   old WAL segments, so ciphertext can linger on disk until overwritten, and the workspace's key
   still opens it for non-closure deletions. Accepted by invariant 10 as written; note it in the
   privacy notes so DEL-2's "even with the highest database privilege" is read with it.
6. **The buyer-data screen keeps identifiers in the mutation cache.** React Query holds the last
   search's identifiers in memory for 5 minutes after the screen closes. `gcTime: 0` on the
   `start` and `exportAccess` mutations (`apps/ui/src/routes/buyer-data.tsx:149,163`).
7. **Two `NOT VALID` constraints stay unvalidated** (db-pii 0006 `blind_index_fields`, db-main 0026
   `erasure_requests_states`). Add `VALIDATE CONSTRAINT` in the next contract migration of each
   database (ADR-045 pattern).
