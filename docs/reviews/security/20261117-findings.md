Commit audited: 110866a (main)   Environment: local   Tooling: Cloudflare security-audit skill @c1c8a8c (light mode)

**Verdict:** no Blocker. One Major (password reset can be switched off for everyone). M02 approval

## Method (short)

Guidance mode, `WEB-PROTOCOL-AND-AUTH.md`, `RESOURCE-EXHAUSTION-AND-AVAILABILITY.md` and the
isolation parts of `DATA-ISOLATION-AND-LIFECYCLE.md`. Read by hand: `apps/web/src/auth/*`,
`contract.ts`, `spa.ts`, `users.ts`, the auth routes, migrations 0011 and 0012 and their store,
`apps/worker/src/auth-mail.ts` and `users-jobs.ts`, `packages/logger/src/logger.ts`. Probed on a
fresh local stack (volumes recreated, `scripts/dev-secrets.sh`) with the DEV ONLY demo sign-in and
synthetic emails. No fuzzing, no load, no sub-agents (Hashir, 17 Nov 2026).

**Trust boundaries:** browser → edge Caddy (replaces client `X-Forwarded-For`) → web (Fastify,
`trustProxy` uniquelocal) → db-main as `ob_app`, which reaches auth tables only through SECURITY
DEFINER functions. Web → queue → worker for every mail; the worker makes reset and invite tokens.
**Inputs:** the public auth routes (`/api/auth/csrf`, `sign-in`, `password/forgot`, `password/reset`,
`invites/:token`, `invites/accept`), the pre-MFA routes, the signed-in routes, and the cookies
`ob_session` / `ob_csrf`.

## Confirmed findings

## S5-20261117-01 — Medium (maps to Major) — Junk reset requests switch off password reset for every user for 24 hours
IDs: USR-7 (supports SEC-1)  CWE/OWASP: CWE-770, OWASP A04 Insecure Design
Evidence:
- `packages/db/migrations/0012_reset_requests.sql:49`: the platform-wide cap (100 allowed per 24 h)
  counts every request marked `allowed`, and `allowed` is decided **before** the email is looked
  up (`apps/web/src/auth/service.ts:678`, then `loginLookup` at :682). So requests for emails that
  have no account use up the cap.
- The per-address cap is 10 per hour (`0012_reset_requests.sql:47`), so 10 client addresses are
  enough to fill it in one burst.
- Reproduction (local db-main, inside `BEGIN … ROLLBACK`):
  ```sql
  SELECT count(*) FILTER (WHERE ok) FROM (
    SELECT app.auth_reset_allow(sha256(('junk'||g)::bytea),
           ('198.51.100.'||(g % 10 + 1))::inet, now() + (g||' seconds')::interval) ok
      FROM generate_series(1,100) g) s;                         -- 100
  SELECT app.auth_reset_allow(sha256('real-victim'::bytea),
         '203.0.113.7'::inet, now() + interval '5 minutes');   -- false
  ```
  Through the API the same is 100 × `POST /api/auth/password/forgot` with random emails from 10
  addresses; each answers 202, and every real user's reset mail after that is silently dropped
  (`auth.reset_capped`, info level).
Impact: an anonymous attacker with 10 IPv4 addresses (or one IPv6 range, see Needs validation 1)
stops all password recovery on the platform, on a rolling 24-hour basis, at almost no cost. Users
who forget their password are locked out; nobody is told.
Required fix: count only mails that are actually sent toward the platform-wide cap. Look the email
up first (the 202 is already answered before the work, so timing stays equal), and mark a request
`allowed` against the global cap only when an account exists and the per-email and per-address caps
pass. Keep the per-email and per-address caps counting every request, as now. Log `auth.reset_capped`
at warn when the **global** cap is hit, so an operator sees it. Test: `[USR-7] junk reset requests
do not use up the platform-wide cap`.
Resolution: (S3 fills in; S4 verifies)

## S5-20261117-02 — Low (maps to Minor) — Sign-in time tells whether an email has an account
IDs: USR-5 (supports USR-7)  CWE/OWASP: CWE-208, OWASP A07
Evidence: `apps/web/src/auth/service.ts:312-320`: a failed sign-in for a real account writes an
`auth.login_failed` row (one more database round trip); an unknown email skips it. argon2 runs in
both cases (`passwords.ts:132-135`), so the gap is only the extra write. Measured on the local
stack, 40 pairs, counters cleared between attempts, all answers 401:

| email | median | mean | sd |
|---|---|---|---|
| real, wrong password | 64.9 ms | 72.2 ms | 27.8 ms |
| unknown | 56.8 ms | 63.5 ms | 18.9 ms |

A gap of about 8 ms at the median, inside the noise of one request but visible over a few dozen.
The lockout (10 per email per 15 minutes, same for real and unknown emails) and the per-address delay
slow this to roughly one email per hour per address; with many addresses it scales.
Impact: account enumeration only (whether a given email uses OmniBridge). No access. USR-7 and
ADR-048 intend the same answer for real and unknown emails, so this is a gap in a stated property.
Required fix: make both paths cost the same round trips. Simplest: give `app.auth_record_failure`
a nullable `p_user` and write the `auth.login_failed` row inside that same call, so a real and an
unknown email each make exactly one call. The lock-time extras (`auth.locked`, `userWorkspaces`,
the lock-notice job) can stay, because by then both kinds of email answer 429 the same way. Test:
`[USR-5] a failed sign-in makes the same database calls for a real and an unknown email`.
Resolution: (S3 fills in; S4 verifies)

## S5-20261117-03 — Low (maps to Minor) — Lock notices have no cap, so known emails can be used to burn the mail quota
IDs: USR-5  CWE/OWASP: CWE-770
Evidence: `apps/worker/src/auth-mail.ts:26-70` mails the locked user and **every admin** of each of
the user's workspaces on every lock (`service.ts:321-335`). A lock lasts 15 minutes, so one known
email can be re-locked about 96 times a day, from one address in about 90 seconds each time (10
failures with the per-address delay). There is no per-user or platform cap on these mails, unlike
reset mail (ADR-020: mail is a paid, capped resource).
Impact: with a few dozen known member emails an attacker sends thousands of lock notices a day to
users and admins: the transactional-mail quota runs out (blocking reset and invite mail), and admins
learn to ignore the notices. Locking the account itself is what USR-5 requires and is not the
finding.
Required fix: at most one lock notice per user per 24 hours (later locks in that window are only
audited), and a platform-wide daily cap on lock notices that logs at warn when hit. Test: `[USR-5]
repeated locks within a day send one notice`.
Resolution: (S3 fills in; S4 verifies)

## Needs validation

1. **IPv6 makes the per-address limits per-host, not per-attacker.** `ip_counters` and
   `reset_requests` key on the exact address (`0011_auth.sql:186,228`, `0012_reset_requests.sql:47`).
   An IPv6 client usually controls a whole /64, so the per-address delay and the 10-per-hour reset
   cap don't hold back an attacker who rotates addresses. **To check:** whether the production edge
   (netcup, `infra/edge/sites/omnibridge.caddy`) serves IPv6. If it does, group IPv6 addresses by /64
   in both counters. This makes S5-20261117-01 and -02 cheaper but doesn't change their fix.
2. **SEC-12 "alerts on unusual logins".** No alert rule reads `auth.login_failed` / `auth.locked`
   anywhere in `infra/` or the apps. **To check (S1):** which module owns the SEC-12 login alerts
   (M22 observability?) and that the backlog has them.

Rejected after testing (for the record): login CSRF and cross-site POST (no Origin, a foreign Origin
or a missing token all give 403); a CSRF token from another browser on a session route (403, because
the header must match the session's own hash); pre-MFA cookie on signed-in or workspace routes (401);
the old pre-MFA token after MFA (401, because the token is replaced); TOTP replay from a second
session (401, `auth_mfa_use_step`); the old session after sign-out (401); workspace switch to a
workspace the user is not a member of (`session_advance` checks membership); a removed member
(`runMember` → `NotAMember` → 401, USR-8); reset link reuse (consumed with every other open link);
reset and invite tokens in logs (the path and `?token=` are redacted); encoded or odd paths (see
below).

**T-0209 paths:** `/%61pi/auth/…` reaches the same API route with the same auth (401 without a
session). `/API/…`, `//api/…`, `/api;/…` and `/Api/users` get `index.html`, which is the static
shell with no data and `no-cache`; no API data or cookie is served through any of them. `/api/x/`
with a trailing slash, `%2F` and `%00` give the JSON 404. `/healthz` and `/webhooks/**` stay at the
root as intended.

## Hardening notes

1. **Cookie prefix.** `ob_session` and `ob_csrf` have no `__Host-` prefix (`cookies.ts:38-44`). They
   are host-only already (Path=/, no Domain). The prefix would also stop a sibling host such as
   `omnibridge.co.uk` / `www` (the public site) from tossing a `Domain=omnibridge.co.uk` cookie onto
   the app (session fixation into an attacker's account). One-line change on both cookies plus the
   SPA's cookie read.
2. **Platform stage is not re-checked.** `resolvePlatform` (`service.ts:190-196`) trusts the session
   stage and doesn't re-read `platform_admin`. There's no demotion path today (M05). When one lands,
   re-check it per request or revoke the user's sessions on demotion, as T-0204 does for members.
3. **Password change leaves open reset links valid.** `changePassword` (`service.ts:757`) doesn't
   mark open `password_resets` rows used. Low value to an attacker (they would need the mailbox),
   but a one-line `UPDATE … SET used_at` in `auth_password_set` closes it.
4. **Minimum age blocks resetting.** `resetPassword` applies the 1-day minimum age
   (`service.ts:711,720`): someone who changed their password today and then forgot it can't reset
   until tomorrow. Not a security hole, but it pushes people to support. S1 to decide if USR-3's
   minimum age should apply to resets.
5. **Targeted lockout.** Anyone who knows an email can keep that account locked (USR-5 as written).
   Accepted by the PRD. Note it in the ops runbook, so support knows the answer is "wait or reset".
6. **CSP and inline styles** (known, T-0209 follow-up). `style-src 'self'` blocks the SPA's inline
   `style=` attributes. I found no security angle: the risk is that someone "fixes" it with
   `'unsafe-inline'` on `style-src`. Prefer moving styles to classes, or `style-src-attr` with
   hashes. Never `'unsafe-inline'` for scripts.
7. **Case and slash variants of `/api`.** `spa.ts:51` treats `/API/…` and `//api/…` as pages. They're
   harmless now, but answering the JSON 404 for any path whose first segment is `api`, ignoring case,
   would keep "API-looking" paths out of the SPA and its cache rules.
